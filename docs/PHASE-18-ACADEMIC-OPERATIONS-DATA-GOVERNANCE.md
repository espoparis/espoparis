# Phase 18 — Academic Operations & Data Governance

## Purpose
Phase 18 turns the Academic Control Center from a feature list into an operational model that can survive staff turnover, yearly curriculum changes, multilingual admissions, imports, grades, attendance, progression and offline/online payments without creating multiple competing student databases.

## Source-of-truth hierarchy
1. **Central Enrollment Database** — canonical application/student identity, application ID, verified email, admission status, academic placement and lifecycle.
2. **Website application database** — internal user account/session identifiers, portal entitlements, academic record projections, payment events, audit log and student-facing views.
3. **Google Classroom** — live teaching, class communication, assignments and teacher workflow. It is not the authoritative student registry.
4. **Google Drive** — content storage and controlled file access. It is not the authoritative student registry or gradebook.
5. **Google Forms and language spreadsheets** — admission intake sources. They feed the Central Enrollment Database but do not independently determine the student's current academic state after import.

## Canonical identity
A student may have multiple identifiers with different jobs:
- `applicationId` / institutional student number, for administration and human-facing references.
- `internalUserId`, generated by the web application, for secure database relationships.
- verified email, used as the first matching bridge between an accepted enrollment and a website account.

Never use a displayed student number as an authentication secret.

## Admissions data pipeline
Expected pipeline:

Google Form → language-specific spreadsheet → Central Enrollment Database → validation/matching → student account link

Before production linking, audit every language pipeline. Required canonical fields include at least:
- application/student ID
- full name
- verified email
- application language
- academic year
- admission status

The currently reported issue where some central rows receive email/details but not the full name must be treated as a pipeline defect. The Phase 18 validator explicitly blocks a row with a missing name from becoming import-ready.

## Duplicate control
Before an import can create/update records:
- application IDs must be unique;
- emails are normalized case-insensitively;
- missing required fields are blocking errors;
- repeated emails are surfaced for manual review;
- unknown lifecycle statuses are warnings until mapped.

No import should silently overwrite an existing student.

## Academic operator roles
Recommended operational roles:

### Teacher
Can view assigned students, enter draft grades and record attendance. Cannot publish final grades or promote students.

### Academic Officer
Can manage enrollments, curriculum drafts, grades, attendance, progression and academic entitlements.

### Finance
Can review payment records and confirm authorized offline payments. Cannot edit curriculum or academic results.

### Editor
Manages public/editorial content only. No academic-record authority.

### Administrator
Full administrative authority, still subject to server-side authentication and audit logging.

## Grades
Grades have draft/published separation. A student-facing transcript must display only `published=true` records. Teachers may enter drafts while the academic office controls publication.

## Attendance
Attendance supports `present`, `absent`, `excused`, and `late` states. Attendance policy thresholds are intentionally not hard-coded yet because the Center has not provided an approved institutional rule. Phase 18 computes summaries but does not automatically fail/promote a student based on attendance.

## Progression
The system may recommend progression after results are complete. Final decisions remain approval-based:
- promote
- repeat
- hold
- complete program

After an approved promotion, the next term/year can be activated automatically and its course access generated from the active curriculum version. Historical records remain unchanged.

## Curriculum changes
Curriculum is versioned by academic year. Active/archived curriculum versions are immutable from normal editing. Changes for a future cohort are made in a new draft version. This prevents a renamed or removed subject from rewriting the historical record of earlier students.

## Audit log
Sensitive changes must produce an audit event in the same transaction as the underlying mutation. Audit scope includes:
- student/enrollment changes
- curriculum changes
- grade publication
- attendance corrections
- progression approvals
- offline payment confirmation
- entitlement grant/revocation

Store actor, entity, timestamp, source, reason and before/after state where appropriate.

## Payment boundary
Academic enrollment and commercial/course purchase remain separate. Confirming payment may create an entitlement, but it must never create an academic enrollment. Conversely, an accepted academic student receives included academic-course access without purchasing each course individually.

## Annual operating cycle
1. Close the current term after grades/attendance are complete.
2. Academic office reviews results and recommendations.
3. Approve promotion/repeat/hold/completion decisions.
4. Create/activate the next enrollment term.
5. Assign the curriculum version and course offerings.
6. Synchronize Classroom memberships/links after academic state is authoritative.
7. Keep prior grades, attendance and curriculum references immutable.
8. Archive exports and audit reports.

## Production blockers still open

- Production database provider and migrations.
- Audit of the existing Enrollment Drive, Forms, per-language Sheets and Central Database.
- Fix of the missing-name pipeline defect.
- Confirmed mapping of existing application IDs and statuses.
- Approved grading, attendance and progression rules.
- Payment provider / bank-transfer operating procedure and finance permissions.
- Google Classroom API authorization and course mapping.
